# Benchmarks

> The benchmarking setup was initially generated by Codex with reviews from Claude Code.

These benchmarks compare cfDNAlab with other tools for coverage, fragment lengths, end motifs and midpoint profiles. They compare the calculated values and record how much time and memory each tool uses. Each tool uses its own fragment filters and counting rules, so the comparisons explain which differences are expected even when the tools work correctly.

Install the tools below, then follow [Run the benchmarks](#run-the-benchmarks) to submit the jobs and compare their outputs. The [execution reference](benchmarks_spec.md) lists script settings and saved files. The [comparison reference](benchmarks_concordance_spec.md) describes the calculations and measures of agreement.

## Installation

From the repository root, run `bash benchmarks/install_tools.sh /path/to/benchmark-tools` on Linux x86_64 with Bash 4 or later. Replace `/path/to/benchmark-tools` with the absolute path to a directory reserved for these tools. Use that same directory wherever `/path/to/benchmark-tools` appears in the commands below. Conda, Apptainer, Git, wget and tar must already be installed. Building cfDNAlab also needs GNU make and C/C++ compilers.

The installer puts Conda environments under `envs/`, with downloaded executables, source code, environment archives and the cfDNAPro container image beside that directory. When installation finishes, it writes `tool_paths.sh` in the installation directory. This file contains the paths to the installed tools and Griffin's reference files. The [benchmark commands](#run-the-benchmarks) load these paths before submitting jobs or collecting results.

Installation files stay under the directory passed to the installer. `cache/` holds downloaded packages, Rust dependencies, container layers and font caches. `tmp/` holds temporary build and unpacking files. Configuration and application data use `config/` and `share/`. The installer sets these locations before running Conda because `--prefix` alone only selects where the environment is installed. It does not move Conda's download cache. The installer also disables registration in `~/.conda/environments.txt`. These settings affect the installer and programs it starts, leaving the calling shell and any existing caches unchanged.

Compute nodes need Slurm to run the jobs, GNU time at `/usr/bin/time` to measure the commands, GNU coreutils for file operations and `ldd` to check shared libraries. Python 3 runs setup commands before timing begins.

The installation choices below were checked against the linked guides and package recipes on **2026-10-29**. The installer requests the listed versions so later runs can use the same software. Installation on the Linux cluster remains to be verified.

The Python settings appear once in the installer and again in each benchmark job because those are separate shell processes. Running the installer with `bash` does not change the submitting shell's environment.

The installer uses conda-pack to archive complete Conda environments. Each job extracts the environments it needs into local temporary storage and runs `conda-unpack` to update their installation paths before timing. This lets the tools load Python and libraries from the compute node's copy. Copying only an executable could leave it loading files from the original installation. `BENCH_SETUP_PYTHON` (default `python3`) runs these setup commands. FinaleToolkit's command is started with its environment's Python for version checks and measurements, so it does not depend on `python3.11` being on the node's PATH. Every job also unpacks samtools to read the BAM header. Build and pack on the same Linux platform used for benchmarking, as required by conda-pack.

cfDNAlab and PanDepth are copied as executables, so the compute node must already have their required shared libraries. Each job checks for missing libraries with `ldd` before measurements begin. Font availability also needs to be checked for cfDNAlab's default QC plots. The mosdepth executable contains its libraries and does not need this setup.

## Resume or repeat an installation

The installer records each tool's version, installation status and expected files in `manifest.tsv`. Running the installer again skips a completed tool when its version matches and all expected files still exist. A changed version, missing file or `outdated` status causes that tool to be installed again, with a separate log in `logs/`. Cleanup removes only files belonging to that tool. cfDNAlab keeps its compiled build files under `build/cfdnalab/` so later builds can reuse them.

```bash
bash benchmarks/install_tools.sh /path/to/benchmark-tools --only cfdnalab,samtools
bash benchmarks/install_tools.sh /path/to/benchmark-tools --force finaletoolkit
bash benchmarks/install_tools.sh /path/to/benchmark-tools --mark-outdated cfdnalab
```

Use `--force all` to reinstall every tool. If source code or dependencies change without a version change, use `--force` or `--mark-outdated` for the affected tool because the installer does not detect those changes automatically. `--only` limits the selected tools, and `--force` applies within that selection. Without `--only`, all tools are selected. Installed package lists and the container image's identity stay under `records/`. `cfdnalab-build.tsv` records the installed cfDNAlab commit and whether it contained uncommitted changes at build time. The installer includes `BENCH_INSTALL_MANIFEST` and `BENCH_CFDNA_BUILD` in `tool_paths.sh` so jobs can copy these records beside the results. Keep the complete installation records with the benchmark results.

Picard can return exit status 1 for its version command. The installer accepts that documented behavior only when the output identifies version 3.5.0. The FinaleToolkit dependencies and the environments made with conda-pack 0.9.2 still need to be installed and run on Linux to verify that they work together.

## Run the benchmarks

The commands below run the coverage, fragment length, end-motif and midpoint comparisons. Each feature's README explains how its tools count fragments. The commands actually executed are defined in [coverage/commands.sh](coverage/commands.sh), [lengths/commands.sh](lengths/commands.sh), [ends/commands.sh](ends/commands.sh) and [midpoints/commands.sh](midpoints/commands.sh). [experiment_commands.md](experiment_commands.md) shows the tool commands and the calculations inside the helper scripts.

A Slurm job reserves a compute node for the benchmark so other jobs do not compete for its CPU and memory. Within the job, each tool command runs in a separate Slurm step (`srun`) with its own timing, memory and CPU records. The job copies input files and tool environments to the node's local temporary storage before measurements begin, so those transfers are excluded from the tool's runtime.

### Jobs to run

Submit each row in the table at **1, 4, 12 and 32 cores**, giving **24 jobs**. The tools in a job run in sequence. Each available thread or worker option receives the allocated core count directly. Tools without such an option still run at all four core settings, and their CPU use is recorded.

Each tool configuration runs once as a warmup, then three times for measurement. The warmup uses the same inputs and is recorded but excluded from the reported averages. Griffin instead runs its short, untimed release demo followed by a single measured run per core setting.

Four additional checks, described under [When tools include different fragments](#when-tools-include-different-fragments), share three extra jobs at 32 cores. This brings the total to **27 benchmark jobs**.

`MAPQ` is the mapping-quality score recorded by the aligner. The fragment length bounds below include both endpoints. Matching these thresholds reduces selection differences, but tools can still use different pairing rules or lack a corresponding filter, as explained below.

| Job | Tools | Filters | Purpose |
| --- | --- | --- | --- |
| Coverage | cfDNAlab, mosdepth, samtools, PanDepth, FinaleToolkit | MAPQ >=30, inclusive lengths 30-1000 bp | Compare read depth, fragment coverage, regional read depth and regional fragment counts separately. cfDNAlab uses its usual pairing rules. A separate run measures its usual autosome-only setting. |
| Fragment lengths | cfDNAlab, cfDNAPro, FinaleToolkit, samtools, Picard | MAPQ >=30, inclusive lengths 30-1000 bp | Compare fragment length histograms, retaining each tool's own fragment definition and pairing rules. |
| End motifs | cfDNAlab, FinaleToolkit, cfDNAPro | MAPQ >=30, inclusive lengths 30-1000 bp, 4-mers | Compare 4-mers taken from the reference sequence. cfDNAPro counts only left ends, so comparing its frequencies with tools that count both ends is approximate. |
| Midpoint profiles without GC correction | cfDNAlab | MAPQ >=20, inclusive lengths 100-200 bp | Calculate uncorrected profiles for comparison with Griffin's uncorrected output. |
| Midpoint profiles with GC correction | cfDNAlab | MAPQ >=20, inclusive lengths 100-200 bp | Estimate sample GC bias, then calculate corrected profiles for comparison with Griffin's corrected output. |
| Midpoint profiles, both versions | Griffin | MAPQ >=20, inclusive lengths 100-200 bp | Estimate sample GC bias and calculate profiles. The same run produces both uncorrected and GC-corrected outputs. |

The coverage job compares four quantities. Read depth counts aligned read bases, while fragment coverage also fills the gap between mates. The regional runs summarize read depth or estimate fragment counts within shared 500 kb windows. Each quantity is compared with the corresponding quantity from the other tools.

For fragment lengths, cfDNAlab measures the span from the forward alignment's start (`forward.pos`) to the reverse alignment's end (`reverse.reference_end`). Several competitors instead use the template length recorded in the BAM (`TLEN`), which can give a different histogram even on the same input.

The midpoint jobs compare cfDNAlab against Griffin twice: without GC correction and with GC correction. All three jobs use the same BAM and sites. They count fragment midpoints around sites supplied in a BED file, with a label identifying each site's group. Both tools use 9,990 bp windows around these sites, 15 bp bins and 165 bp smoothing.

The GC-corrected midpoint jobs first estimate the sample's GC bias, then apply that estimate when counting midpoints. cfDNAlab uses the same exclusion BEDs for its reference GC calculation, sample GC estimation and midpoint profiles. Estimation uses a wider fragment length range than profiling: normally 30-1000 bp for cfDNAlab, inherited from its reference GC distribution, and 15-500 bp for Griffin. Both tools calculate the profiles from 100-200 bp fragments. Each estimator keeps its tool's usual range because that range determines which data are used to fit and smooth the bias estimate. The [midpoint README](midpoints/README.md#gc-corrected-comparison) describes the calculations and reference files.

#### When tools include different fragments

Tools can include different fragments from the same BAM. FinaleToolkit's coverage, length and end-motif commands, and mosdepth's fragment mode, include only alignments marked as properly paired by the aligner. The proper-pair flag (`0x2` in SAM/BAM) records this classification according to the aligner's criteria. cfDNAlab normally reconstructs fragments from both alignments and applies its own pairing, orientation, quality and length checks. A pair can pass these checks without the flag, so matching MAPQ and length bounds alone does not make the tools count the same fragments.

The additional cfDNAlab runs use `--require-proper-pair` to match this selection rule. Comparing their outputs with the same competitor shows whether excluding pairs without the flag brings the results closer. Other counting differences remain. For example, cfDNAlab checks both mates and reconstructs their aligned span, while FinaleToolkit uses the first mate (`read1`) and TLEN. Each feature's README explains the remaining differences.

These extra runs provide outputs for comparison. Each runs once at 32 cores, without a warmup, using the same MAPQ and length bounds as the other runs. The repeated timing results come from cfDNAlab's usual configuration. The two coverage checks share a job, and lengths and end motifs each have a separate job.

| Additional 32-core agreement check | Compared with |
| --- | --- |
| Coverage `cfdnalab-fragment-proper` | `mosdepth-fragment` |
| Coverage `cfdnalab-region-counts-proper` | `finaletoolkit-coverage` |
| Lengths `cfdnalab-proper` | `finaletoolkit` |
| End motifs `cfdnalab-reference-proper` | `finaletoolkit` |

The main cfDNAlab coverage, length and motif commands process every reference sequence listed in the BAM. The additional `cfdnalab-autosomes` coverage run measures its usual setting restricted to autosomes, so it processes fewer chromosomes.

The tools cannot all apply the listed filters in the same way. PanDepth has no fragment length filter. Picard has no MAPQ option, so its timed command uses its own selection rules. After timing, a separate Picard run with the common filters produces the histogram used for comparison. cfDNAPro has no motif length-filter option, so the R helper filters its fragment object before counting motifs, within the timed command. It can only calculate motifs on reference sequences present in its bundled genome package. The results record these differences in the fragments included.

Each successful cfDNAPro motif run saves [times for its individual steps](ends/README.md#cfdnapro-motifs) in `runs/<run_order>/cfdnapro-stage-timings.tsv`. This shows how much time the benchmark's R length filter adds to cfDNAPro's BAM reading, fragment construction and motif counting. The total runtime includes that filtering cost.

### Set the input paths and cluster settings

Create `benchmarks/local_settings.sh` to record the paths to your [prepared inputs](data/README.md), where results should be saved and which temporary storage to use on the cluster. Set the variables below using `export NAME=value` so submitted jobs receive them. Keep this file out of Git. Put only settings in it, and run preparation commands and job submissions separately.

| Variable to set in `benchmarks/local_settings.sh` | What it sets |
| --- | --- |
| `benchmark_root` | Parent directory for the new results series |
| `LOCAL_SCRATCH_VAR` | Name of the variable holding the compute node's local scratch directory. Defaults to `TMPDIR` |
| `BENCH_BAM` | Prepared, coordinate-sorted hg38 BAM. Its index defaults to `<BAM>.bai`, or can be set with `BENCH_INDEX`. Coverage, lengths and motifs require a BAI index |
| `BENCH_REF_2BIT`, `BENCH_REF_FASTA` | Matching alignment reference in 2bit and uncompressed FASTA formats. Griffin requires an existing `<FASTA>.fai`, overridable with `BENCH_FASTA_INDEX` |
| `BENCH_INTERVALS` | Prepared grouped 9,990 bp site BED described in the [midpoint input instructions](midpoints/README.md#inputs-and-run) |
| `BENCH_CFDNA_REF_GC` | Package path printed when the [reference-preparation job](#prepare-the-cfdnalab-gc-reference-once) is submitted. Add it to this settings file and use it after preparation succeeds, then reuse it for later benchmark submissions |

Each benchmark job uses temporary storage on the compute node for its input files, tools and intermediate files. The cluster makes the path to this storage available through an environment variable, commonly `TMPDIR` or `SLURM_TMPDIR`. Tell the benchmark which variable to read by setting `LOCAL_SCRATCH_VAR` in `benchmarks/local_settings.sh` to its name, without a `$`:

```bash
# The cluster sets TMPDIR to a local scratch directory when the compute job starts
export LOCAL_SCRATCH_VAR=TMPDIR
```

If the cluster uses `SLURM_TMPDIR`, set `export LOCAL_SCRATCH_VAR=SLURM_TMPDIR` instead. Each job reads the selected variable on the compute node, so its directory need not be known on the login node. The job stops if the variable is unset or empty, or its directory is missing or not writable. Each runner creates its own working directory there and sets `TMPDIR` to its `tmp/` subdirectory for the tools. The selected variable name and directory are saved in `run.tsv`.

### Prepare the cfDNAlab GC reference once

Submit this separate preparation job once before the GC-corrected midpoint benchmarks. It calculates the reference distribution with the same five exclusion BEDs used by sample GC estimation and midpoint profiling. Reuse the resulting package for later submissions with the same alignment reference and blacklist set. Griffin's reference GC tables are supplied by the installer.

The job reserves an exclusive node, runs a single calculation with 32 physical cores, and stages the reference, blacklists and executable on local scratch. The calculation uses an explicit thread count and temporary directory. It uses the same timing and CPU-binding checks as the benchmark jobs. Input staging and saving the completed package are outside its measured time. Its `timings.tsv`, exact command, logs, input checksums and Slurm allocation details stay in the new reference-results directory, outside the feature timing summaries.

Run the block in **Bash 4 or later from the repository root on the login node**. Choose a new output directory and adjust the time limit and node constraint for the cluster. The block returns after submission, printing the job ID and the deterministic package path. Put the printed `export BENCH_CFDNA_REF_GC=...` assignment in `benchmarks/local_settings.sh`, and use the package after preparation succeeds.

```bash
# Copy the whole block, including the surrounding parentheses
(
set -euo pipefail
# Load tool paths from the directory passed to install_tools.sh
# Replace /path/to/benchmark-tools with that directory's absolute path
source /path/to/benchmark-tools/tool_paths.sh
source benchmarks/local_settings.sh
: "${benchmark_root:?Set benchmark_root in benchmarks/local_settings.sh}"

# Choose a new directory explicitly. Existing packages do not determine this path
reference_results="$benchmark_root/references/griffin-blacklisted"
reference_cores=32
# Allow enough time for staging, calculation and saving the package
reference_wall_time="00:30:00"
if [[ -e "$reference_results" ]]; then
    echo "Reference results already exist: $reference_results. Reuse the package or choose a new directory." >&2
    exit 1
fi
mkdir -p "$benchmark_root/references/slurm"
reference_slurm_options=(
    --export=ALL --parsable --exclusive --mem=0
    --cpus-per-task="$reference_cores" --time="$reference_wall_time"
    --constraint=gen6
    --output="$benchmark_root/references/slurm/reference-gc-%j.out"
    --error="$benchmark_root/references/slurm/reference-gc-%j.err"
)
if [[ -n ${BENCH_EXPECTED_NODE:-} ]]; then
    reference_slurm_options+=(--nodelist="$BENCH_EXPECTED_NODE")
fi
# Submit preparation without waiting for a node or for the calculation to finish
BENCH_CORES="$reference_cores" BENCH_RESULTS="$reference_results" \
    sbatch "${reference_slurm_options[@]}" benchmarks/midpoints/prepare_reference_gc.sh

# The package name is fixed by prepare_reference_gc.sh
# Add this assignment to local_settings.sh and use it after the job succeeds
printf 'export BENCH_CFDNA_REF_GC=%q\n' "$reference_results/griffin_blacklisted.ref_gc_package.zarr"
)
```

### Submit the jobs

Once the inputs and settings are ready, adjust the time limits and Slurm options described below for your cluster. Then run the submission block in **Bash 4 or later from the repository root on the login node**.

The six time limits below apply to **complete jobs**, including setup, every selected command's repetitions and any output comparison. For example, the coverage limit covers cfDNAlab and all selected coverage competitors together. Each midpoint limit covers its separate job. These values specify how long Slurm allows the jobs to run. They are not measured runtimes, and each must allow its job to finish at the slowest core setting. The extra 32-core checks reuse their feature's limit but run only once.

Griffin needs enough time for the demo, setup, sample GC estimation and profiling. If that takes more than 47 hours, select a Slurm partition and time limit that allow it to finish. If the other tools cannot all finish within a partition's job limit, divide their method list between separate jobs with new result directories, keeping every selected tool and core setting.

`--constraint=gen6` selects the node generation used for these benchmarks. Change it and add a Slurm partition to `slurm_options` as needed for the cluster. Use the same physical node when available. Setting `BENCH_EXPECTED_NODE` both adds `--nodelist` below and makes each job check its hostname. If jobs use different nodes, choose equivalent hardware and keep their recorded node names with the results, because differences between machines can affect timing.

```bash
# Copy the whole block, including the surrounding parentheses
# The parentheses keep the error settings below out of your interactive shell
(
set -euo pipefail
# Load tool paths from the directory passed to install_tools.sh
# Replace /path/to/benchmark-tools with that directory's absolute path
source /path/to/benchmark-tools/tool_paths.sh
# Load the input paths and cluster settings saved in this repository
source benchmarks/local_settings.sh
: "${benchmark_root:?Set benchmark_root in benchmarks/local_settings.sh}"

# Limits for the complete multi-method jobs, including cfDNAlab and competitors
coverage_wall_time="11:00:00"
lengths_wall_time="11:00:00"
end_motifs_wall_time="11:00:00"

# Limits for the three midpoint workloads, applied to each submitted job
midpoints_uncorrected_wall_time="11:00:00"
midpoints_cfdnalab_gc_wall_time="11:00:00"
midpoints_griffin_gc_wall_time="1-23:00:00"

# Reserve the node and run each configuration once for warmup, then three times
# Griffin overrides this schedule below to use one measurement per job
# Its runner replaces the full-input warmup with the short untimed demo
export BENCH_PILOT=0
export BENCH_WARMUPS=1 BENCH_REPETITIONS=3
# Preserve an invocation timeout from local settings, defaulting to disabled
export BENCH_RUN_TIMEOUT_SECONDS=${BENCH_RUN_TIMEOUT_SECONDS:-0}
export BENCH_MIN_MAPQ=30 BENCH_MIN_LENGTH=30 BENCH_MAX_LENGTH=1000
export BENCH_K=4 BENCH_GENOME=hg38

# Create a new series and feature parents, leaving each job's directory uncreated
# The runners reject existing BENCH_RESULTS directories and create their own
mkdir -p "$benchmark_root/results"
results_root=$(mktemp -d "$benchmark_root/results/run-$(date -u +%Y%m%dT%H%M%SZ)-XXXXXX")
results_root=$(cd "$results_root" && pwd)
mkdir -p "$results_root"/{coverage,lengths,ends,midpoints,concordance,slurm}
mkdir -p "$results_root/midpoints"/{cfdnalab,cfdnalab-gc,griffin-gc}
# Run this printed assignment in your shell before collecting results
printf 'results_root=%q\n' "$results_root"

# --parsable prints job IDs, saved below to retrieve memory and status records
# Each job writes its Slurm logs outside the directory created by the runner
slurm_options=(
    --parsable
    --constraint=gen6
    --output="$results_root/slurm/%x-%j.out"
    --error="$results_root/slurm/%x-%j.err"
)
if [[ -n ${BENCH_EXPECTED_NODE:-} ]]; then
    slurm_options+=(--nodelist="$BENCH_EXPECTED_NODE")
fi

# Each list names the tool configurations to pass to BENCH_METHODS below
# Several configurations can use the same tool, such as cfDNAlab's read depth and fragment coverage
coverage_methods=(
    # Read depth, counting overlapping mates once where the tool supports it
    cfdnalab mosdepth samtools-depth pandepth
    # Measure read-depth runtime with cfDNAlab's usual autosome-only setting
    cfdnalab-autosomes
    # Fragment coverage without the additional proper-pair requirement
    cfdnalab-fragment mosdepth-fragment
    # Regional read depth computed directly in shared 500 kb windows
    cfdnalab-regions mosdepth-regions samtools-regions pandepth-regions
    # Regional fragment counts without the additional proper-pair requirement
    cfdnalab-region-counts finaletoolkit-coverage
)
length_methods=(
    # cfDNAlab and cfDNAPro calculate length from the two mate alignments
    cfdnalab cfdnapro
    # Other tools calculate histograms from the BAM's recorded template lengths
    finaletoolkit samtools picard
)
end_methods=(
    # Reference-derived 4-mers without requiring proper pairs
    cfdnalab-reference
```

Each job creates a new results directory with the following files:

| File or directory | Contents |
| --- | --- |
| `run.tsv` | Job settings, input paths and benchmark revision |
| `timings.tsv` | A row for every attempted tool run, including warmups and failures |
| `runs/<run_order>/` | The exact command and its standard output and error logs |
| `profiles/<method>/` | Outputs saved from each configuration's first measured run, for comparison |
| `progress.log` | Setup progress, run starts and completed saves |

Coverage, lengths and motifs compare their saved outputs automatically after all selected tools have run, when at least two outputs measure the same quantity. Their agreement measures are saved in `concordance.tsv`. Coverage also saves the distribution of depth differences between tools, called residuals, and the overlap of bases with nonzero coverage, measured by the Jaccard index. The proper-pair checks and midpoint tools run in separate jobs, so the commands below bring their saved outputs together for comparison. They reuse those outputs without rerunning the tools.

### Collect and compare the results

After all submitted jobs have finished, run the collection block in **Bash 4 or later from the repository root on the login node**. It retrieves Slurm's memory and exit-status records, matches them to each tool run, writes timing summaries, and compares outputs saved in separate jobs. Slurm keeps these resource records in its accounting database, and final values can arrive after a job ends. Collecting them here keeps this work outside the tool measurements.

```bash
# First run the results_root=... assignment printed by the submission block
# Copy this whole block, including the surrounding parentheses
# The parentheses keep the error settings below out of your interactive shell
(
set -euo pipefail
# Load tool paths from the directory passed to install_tools.sh
# Replace /path/to/benchmark-tools with that directory's absolute path

# Keep the downloaded Slurm records with the summaries calculated from them

printf 'analysis_root=%q\n' "$analysis_root"

# Retrieve memory and exit-status records for every job and its measured steps
# The saved sbatch --parsable output may include a cluster name after a semicolon
# Keep only the job IDs and join them with commas for sacct
job_ids=$(cut -d ';' -f 1 "$results_root/job-ids.txt" | paste -sd, -)
sacct -j "$job_ids" --parsable2 --units=K \
    --format=JobIDRaw,NTasks,MaxRSS,State,ExitCode \
    > "$analysis_root/accounting.tsv"

# Keep each feature's timing summaries and every original row together
for feature in coverage lengths ends; do
    mkdir -p "$analysis_root/$feature"
    python3 benchmarks/summarize_timings.py \
        "$results_root/$feature/"*cores/timings.tsv \
        --accounting "$analysis_root/accounting.tsv" \
        --runs-output "$analysis_root/$feature/runs-with-memory.tsv" \
        > "$analysis_root/$feature/summary.tsv"
done

# Summarize the midpoint jobs together, using their shared inputs
mkdir -p "$analysis_root/midpoints"
python3 benchmarks/summarize_timings.py \
    "$results_root/midpoints/"*/*cores/timings.tsv \
    --accounting "$analysis_root/accounting.tsv" \
    --runs-output "$analysis_root/midpoints/runs-with-memory.tsv" \

    "$analysis_root/concordance/coverage/regions.bed"

    ln -s "$results_root/$feature/32cores/profiles/finaletoolkit" \
        "$analysis_root/concordance/$feature/profiles/finaletoolkit"
done

PATH="$(dirname "$BENCH_COMPARE_PYTHON"):$PATH" \
```

## How time and memory are measured

Timing summaries use successful measured runs. The original tables also keep warmups, debugging runs and failures, along with the tool versions, filters, chromosomes processed, run order, start times, node names and assigned CPUs. These records let reviewers check which runs were included and what each measured.

The allocated core count and the tool's thread or worker argument are recorded separately. For example, mosdepth's thread option controls BAM decompression, while coverage calculation runs separately. Each Slurm step checks that it is on the expected node and has the requested number of physical cores. Enforcement of CPU limits across child processes also depends on the cluster's Slurm settings for Linux control groups (`cgroups`).

The measurements distinguish the command's runtime from the time needed to finish pending writes. A command can exit while some output is still buffered in memory. The job therefore records the command's elapsed time, then separately times `sync -f`, which asks the filesystem to finish writing. Keeping both values shows how much of the total is spent waiting for writes after the command exits. CPU-time totals also show how much the command uses its allocated cores.

| Columns | Meaning |
| --- | --- |
| `wall_seconds`, `user_seconds`, `system_seconds` | GNU time's elapsed seconds, CPU seconds in user code and CPU seconds in the operating system, respectively. These measure the complete command or pipeline, including writing and compressing its outputs. |
| `flush_seconds` | Time for `sync -f` to finish pending writes on the output filesystem after the command exits. This can include other filesystem writes. |
| `process_plus_flush_seconds` | Command elapsed time plus the time spent finishing filesystem writes. The flush covers the filesystem, so it can include writes from other processes as well as the tool. |
| `output_directory_bytes` | Total size in bytes of the output directory after the run, including final results and intermediate files still present, such as Griffin's temporary bigWig tracks. Measured with `du -sb`, using file sizes rather than allocated disk space. Files outside this directory, deleted files and repeated writes are excluded. |
| `max_rss_kib` | Peak resident memory (RSS) reported by GNU time, in KiB. It is kept separately from Slurm's memory measurement. |
| `tool_exit_code`, `step_exit_code`, `pilot` | Exit statuses for the command and Slurm step, and whether the run used shared-node debugging mode (`pilot=1`). Unavailable measurements are `NA`. |

The [result collection commands](#collect-and-compare-the-results) retrieve Slurm's records for all jobs together and save the downloaded table alongside the summaries.

Combine timing tables only for the same feature and biological input. Collect records for several jobs with `sacct -j ID1,ID2`. The summary matches each run to its exact job and step IDs and reports sample size, mean, standard deviation, median and quartiles for each configuration. Tool versions, nodes and command settings remain separate groups. `runs-with-memory.tsv` keeps the individual runs and failures, so a summary can be traced back to its measurements. Missing Slurm values stay `NA` until records are collected again.

Use `slurm_max_rss_kib` as the main memory measurement and report how the cluster collects it. Slurm's memory measurement can depend on how often it samples, whether it includes child processes and whether it counts memory used to cache files. `slurm-config.txt` records the available settings. In particular, Slurm with cgroup v2 can include file cache in MaxRSS. Check the cluster's settings once and describe them with the results. Memory values are retrieved after the job, without adding a monitoring process to the timed command. See [Slurm sacct](https://slurm.schedmd.com/sacct.html) and [cgroup v2 limitations](https://slurm.schedmd.com/cgroup_v2.html#limitations).

Effective cores are `(user_seconds + system_seconds) / wall_seconds`. This estimates how many cores were busy on average during the command. Divide by `cores` for allocated utilization. For example, 1 effective core in a 4-core allocation corresponds to 25% utilization. Use process wall time for this denominator, rather than the flush-inclusive duration.

Copying inputs and environments, starting the Slurm step, saving comparison outputs, cleanup and comparing results are excluded from the tool measurements. The first measured outputs are copied **after srun returns**, so that copy does not increase the tool step's recorded memory peak. Jobs do not clear filesystem caches between runs. Copying files to the node before timing does not guarantee that the entire input remains cached in memory.

If a command fails, runs on unexpected CPUs, omits an expected output or fails to finish its writes, the job records the failure and skips that configuration's remaining repetitions. It continues with the other selected configurations, then returns a nonzero exit status. The failed run's command and logs remain under `runs/<run_order>/`. Errors during setup or while saving result records stop the job immediately. If Slurm or the operating system kills the job, it may have no opportunity to save the active run or continue. Records saved before that point remain available.

The job creates its results directory, `timings.tsv` header and `run.tsv` before copying inputs. `progress.log` records environment unpacking, file copying, run starts and completed saves, and prints the same messages to Slurm's output. If `timings.tsv` contains only a header, no completed run has been saved yet. Check `progress.log` to see whether the job is still setting up or running a tool. Coverage and lengths check tool versions before copying the BAM, so a broken tool command fails before that large transfer.

`BENCH_RUN_TIMEOUT_SECONDS` limits an individual tool command, separately from Slurm's limit for the whole job. Its default of `0` disables this command limit. A positive integer runs the command under GNU `timeout --verbose --kill-after=60`, inside GNU time, and the limit is recorded in `run.tsv`. Allow time before the job ends for the additional 60 seconds before a forced stop, finishing filesystem writes and saving results.

Exit status 124 usually means the command reached its limit. Status 137 can also result from another forced termination, so keep the error logs and Slurm records to determine what happened. Runs that time out remain in the records but are excluded from averages of successful runs.

## Checking the benchmark code

The automated tests run in a Linux shell without submitting Slurm jobs. They replace the scheduler commands and benchmark tools with small local programs, then check how the scripts handle commands, outputs and failures. Inputs are small files created in temporary directories, so the tests do not need the benchmark BAM, reference files or installed tools.

The tests in [test_runners.py](tests/test_runners.py) check tool commands, timing settings, saved outputs, Picard's extra filtered run, midpoint site preparation, CPU checks and failure handling. They also run complete lengths and Griffin jobs with a replacement for `srun`. The tests in [test_benchmarks.py](tests/test_benchmarks.py) check output comparisons, installation and BAM preparation. These include chromosome selection, coverage differences at individual bases, regional counts, matching runs to Slurm records and cfDNAPro's left-end motif counts. [Additional tests](tests/test_review_regressions.py) check job submission, automatic output comparisons, incomplete debugging reports, length boundaries and empty midpoint profiles. Expected numerical results are derived by hand from the small inputs.

The complete test suite needs Python >=3.11, Bash >=4, GNU time at `/usr/bin/time`, GNU coreutils and `zstd` on PATH. The local Python package supplies the libraries needed to compare outputs, and pysam is needed for BAM reconstruction tests. From the repository root, with Conda available:

```bash
conda create -n benchmark-tests -c conda-forge python=3.11 pip zstd pysam
conda activate benchmark-tests
python -m pip install ./py-cfdnalab
python -m unittest discover -s benchmarks/tests
```

An existing comparison environment can also run the tests. Without pysam, the BAM reconstruction tests are skipped. Tests of Linux-specific job behavior are skipped on macOS, so use Linux for the complete suite. The commands above assume Bash and the GNU system utilities are already installed.

The tests check the benchmark code. Checking installed libraries, fonts, actual CPU assignments and Slurm memory records also requires the tools to run on a compute node. No measured benchmark results are included in these documents. The result tables are templates to fill from the measured runs.

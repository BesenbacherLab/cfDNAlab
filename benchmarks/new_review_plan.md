# Plan for the new Claude benchmark review

This assesses [new_claude_review.md](new_claude_review.md) against the current source, rather than accepting the review's opening decisions as authorization. Implementation and verification results are recorded in [codex_review.md](codex_review.md). All work stays under `benchmarks/`. Tests are prepared for the repository owner, not executed.

## Fix now

1. **Recorded failures should not discard unrelated methods (Claude 1.1).** Preserve the attempted run's row and diagnostics, skip the remaining repetitions of that method, continue other selected methods, and return a failed overall job status. Setup and results-bookkeeping failures remain fatal. Continuation cannot be guaranteed if Slurm or the kernel kills the batch shell itself.
2. **Add an explicit per-run timeout mechanism (1.2).** Support a nonnegative `BENCH_RUN_TIMEOUT_SECONDS`, with zero disabling it until a limit is chosen. Time the timeout wrapper and its descendants, record the configured limit in job metadata, preserve timeout diagnostics and handle failure like other unsuccessful attempts. Do not claim every SIGKILL is a timeout. Actual timeout values need discussion below.
3. **Require an explicit method block (1.3).** Remove all four runners' default method lists. An absent or empty `BENCH_METHODS` fails before staging. This prevents accidentally requesting the entire expensive method matrix.
4. **Make incomplete pilot estimates reviewable (1.7).** Write a per-configuration budget using the actual requested warmup/repetition counts and margin. Include failed configurations with unavailable budgets, identify unsuccessful attempts, and label the successful subtotal as incomplete. Do not present a partial total as a complete allocation estimate.
5. **Preflight coverage scopes (1.8).** Detect a mismatched or empty scope before decompressing/spooling whole-genome tracks. Preserve the current explicit `--common-scope` choice until automatic intersection is agreed. Evaluated scope remains recorded per comparison.
6. **Remove actual single-core-setting leftovers (6).** Remove `cores_to_run`, redundant per-core loops and capture-core selection from all runners and shared preservation. Keep the core count in persisted timing/order rows for provenance. Do not remove unrelated input/scientific validation.
7. **Prepare meaningful regressions (7).** Cover failure continuation, native exit/signal handling, timeout accounting, partial/all-failed pilot reports, fail-fast scope checking, samtools length boundaries, Picard without FR, and midpoint parsing/empty profiles where the installed comparison dependencies permit. Expectations are derived before execution. No test runs.
8. **Update current documentation.** Record changed execution behavior and limits, keep existing agreed settings explicit, and remove contradictory claims. Do not reorganize all documentation or move anything outside `benchmarks/`.

Measurement invariants: successful native commands keep the same biological filters, pairing definitions, outputs and process/flush boundaries. A skipped attempt produces no invented measurement. Failed/timed-out attempts cannot enter successful production averages. Coverage MAE and Pearson stay at base resolution, and residual output stays an aggregated histogram. No input BAM or user-provided midpoint BED is regenerated or changed.

## Decisions and current user direction

The user clarified D1-D6 after the review. The notes below retain every point and distinguish accepted direction from details left for Monday. This follow-up updates documentation only. The runner/comparator changes below are still pending, including replacing the implemented 2+5 defaults with the agreed 1+3.

- **D1: Repetitions (review 1.5 and section 3), agreed.** Use **one warmup plus three measurements**, with Griffin's warmup exception in D2. Update runner/estimator defaults, examples, budget arithmetic and relevant fixtures together. The current scripts still use 2+5. Claude's illustrative totals remain estimates, not measured bookings.
- **D2: Serial tools and job packing (1.6 and 3), partly settled.** Griffin gets its own jobs and must be allowed to finish beyond 24 hours. Do not spend a roughly 30-hour run on warmup. Plan zero full Griffin warmups and three measurements, with the exact split across jobs still open. If a run actually takes 30 hours at a setting, three measurements take roughly 90 hours total at that setting before overhead. One measured repetition per job is an option. Other packing, serial-tool settings and cross-node pooling remain open. Keep exactly one core setting per job. The 30-hour runtime is currently an estimate, not a measurement of our input.
  Cache preparation remains open. The user suggested running Griffin on its 1000-interval demo as a possible short warmup. It would exercise startup and read BAM/FASTA data around those intervals, but the benefit for caching the much larger production input is uncertain. Keep this as a potential warmup, with no decision yet to use it. An untimed cfDNAlab invocation on the same node and staged BAM could warm the pages it reads, but its current midpoint baseline does not read Griffin's FASTA. A simple untimed read of the staged BAM and FASTA is another option if full-input caching is actually needed. Linux page cache is reclaimable, so none of these guarantees residency. See the [kernel page-cache and reclaim description](https://docs.kernel.org/admin-guide/mm/concepts.html#page-cache). No full Griffin warmup is planned, and no extra cache machinery is justified by the current unmeasured concern.
- **D3: Core allocation and native thread arguments (1.4), settled.** Allocate N cores and set native thread/core/worker options to use that budget. Respect options documented as additional threads, where N-1 plus the main thread represents an N-core budget. Methods without such an option still run at their selected core settings. The nested-library-thread example was hypothetical, with no evidence of an actual problem in these workloads. Do not add a separate policy or machinery for it. Reconcile the current feature-specific library environment overrides with this simple native-resource policy during implementation. Keep D3 for traceability, not as an unresolved experimental decision.
- **D4: Midpoint sites/window/normalization (4), site source agreed.** Use [Griffin's public paper site set](https://github.com/adoebley/Griffin_analyses/tree/75467e438a88029206d8d778ddce05eb0ab6efa8/sites/TFBS/10000_unfiltered_sites_CIS_BP_v2) at the linked revision. Its public provenance and large size are part of the intended benchmark. Verify actual file/row counts before reporting them. Keep window width, normalization and any pilot subsets open for Monday. The benchmark still consumes the supplied BED and does not independently select sites or impose 2 kb windows. Source-based full-set runtime and memory estimates remain unmeasured.
- **D5: FrEIA left ends (5), direction accepted.** Use the intact default left-end workflow because the pinned both-end aggregate is broken. Compare native left-end frequencies and/or use doubled left-end counts as an explicitly labeled estimate of both-end counts under the mirrored-side assumption. Doubling leaves frequencies unchanged. Keep the native left counts so observed and estimated totals remain distinguishable. Exact reporting and comparator changes remain pending. Do not recover counts from the damaged both-end table or remove the independent worker-size safeguard.
- **D6: cfDNAPro end motifs (5), inclusion accepted.** Add cfDNAPro `callMotif()` to the planned end-motif comparison. It was previously held because the review treated adding a competitor as a decision, rather than an obvious repair. That scope decision is now settled. The user accepts approximate side mirroring for demonstrating similarity if clearly documented. Apply the same explicit labeling to any doubled counts, retain original left counts, and disclose reference/read-source and native selection differences. Matching configuration, reference identity and implementation details remain for Monday.
- **D7: Coverage intersection/storage (1.8 and 6).** Discuss automatic intersection versus explicit scope consent. A plain Counter is simpler than SQLite for integer native depths, but changes the current bounded-memory guarantee for accepted fractional tracks. NumPy chromosome arrays change memory/performance requirements. Neither change is necessary to repair fail-fast scope validation.
- **D8: Timeout values and censored observations (1.2, 3 and 4).** Choose per-job run limits after pilots, leaving termination grace and bookkeeping time below the allocation limit. Decide how timeout lower bounds appear in figures and whether one censored run is sufficient. No arbitrary numerical cutoff is installed.
- **D9: Pooling and validation removal (4 and 6).** Pooling separate physical nodes by CPU model, removing physical-placement/reference/BED/version/value checks, or discarding reconstruction provenance are not straightforward bug fixes. The final review will distinguish redundant checks from those preventing invalid scientific comparisons.
- **D10: Documentation layout (6).** Consolidation may help, but deleting the requested specs or moving the plan to `.AI/docs/future/` conflicts with the instruction to keep benchmarks independent. Keep plans and specs in this folder. Discuss any larger consolidation first.
